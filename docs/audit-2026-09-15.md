## A. Security

### A1 · `activity_series` could be written directly — **closed**

`0008` revoked the direct `UPDATE` on `activities` because it let an organizer write
`joined_count`, `status` and `waitlist_count` through PostgREST. `activity_series` kept a
`FOR ALL` policy over a full write grant, so everything `0008` forbids on a session was
available on the template that generates them: a post-hoc price change, and moving the time,
weekday and venue with people already on upcoming occurrences.

`0013` revokes `UPDATE` and routes changes through `update_series()` and `cancel_series()`.

**Verified after the fix:**

```
activities      | authenticated | DELETE,INSERT,SELECT
activity_series | authenticated | DELETE,INSERT,SELECT
```

The two now match. `INSERT` deliberately stays — creating is not the dangerous verb, and
`createSeries()` uses it; `12_series_mutations_test.sql` asserts creation still works, so a
migration that locked the door on the way in would fail rather than ship.

`update_series()` also propagates to future occurrences nobody has joined, which closes the
silent-divergence half: editing a series never touched the sessions generated from it and
nothing reconciled them.

### A1b · `generate_series_occurrences()` ignored `is_active` — **closed**

Surfaced while writing `cancel_series()`. The generator never checked the flag, so a
cancelled series would have kept producing sessions and `cancel_series()` would have been a
lie the first time anybody used it. Guard added, and asserted in the test.

Worth recording how the fix nearly went wrong: the generator was first rewritten from memory
and silently dropped the `visibility` and `source` columns and the `on conflict` clause. It
is now spliced from `pg_get_functiondef` with exactly one guard inserted. **A function
replaced "in full" should be copied from the database, not retyped.**

### A2 · `is_blocked()` had no test — **closed, and the control was already correct**

`docs/security.md` lists blocking as a control in place. The predicate is called from eight
places and nothing exercised it.

`13_blocking_test.sql` covers both directions across `profiles`, `activities`,
`nearby_activities()` and `join_activity()`, with an uninvolved third person as a control so
a policy that is merely too broad cannot pass. It also asserts the blocked person cannot
delete the block, and that unblocking restores visibility.

**The predicate was correct.** Stated plainly because it is the honest result: the control was
working, it just was not proven.

**The test was then mutation-checked.** Symmetry was removed from `is_blocked()` and the suite
re-run; it failed on the right assertion with the right message, then the mutation was
reverted. A test that has never been seen to fail is a test nobody should trust.

actually worked is a test that fails.

## D. Process

### D1 · The default-privileges trap — documented, not preventable

Supabase's `alter default privileges in schema public grant all on tables to anon,
authenticated` is still in force. **Every table created after `0003` is world-readable on
creation.**

`0012` was the only migration since `0003` to add a table, and it revokes. But that is
discipline, not a mechanism: the next one is equally exposed and nothing will complain.

**Worth doing:** a test that enumerates every table and asserts its grants are intentional
would turn this from a habit into a gate. Not written.

### D2 · CI covers the database well and the client barely

The quality gate — Prettier, ESLint, `tsc --strict` — caught none of the findings in this
audit. Every one came from reading the schema, running a query, or a SQL test. That is the
argument for C1, and the reason the fourteen SQL suites are worth what they cost.
