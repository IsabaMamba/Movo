# Contributing to Movo

This is a small team working part-time. Everything here exists to keep `main` readable and
deployable without ceremony that costs more than it saves.

## Before you start

```bash
npm install
cp .env.example .env
supabase start
npm run db:push
```

## Branches

Branch from `main`. One branch per issue.

```
<type>/<short-kebab-description>

feat/organizer-check-in
fix/waitlist-promotion-order
docs/security-model
chore/repo-foundation
```

`main` is protected in intent: never commit to it directly, and never force-push it.

## Commits

We use [Conventional Commits](https://www.conventionalcommits.org/). Format:

```
<type>(<scope>): <subject>

<body — why, not what>

<footer — issue refs, breaking changes>
```

**Types:** `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`,
`chore`, `revert`.

**Scopes** follow the module the change lives in: `discover`, `activities`,
`participation`, `communities`, `moderation`, `auth`, `db`, `ci`, `docs`.

Good:

```
feat(participation): promote waitlist head when a joiner cancels

A cancellation previously left a paid-for cancha slot empty until someone
noticed. leave_activity now promotes the first waitlisted user in the same
transaction and queues a notification.

Closes #24
```

```
fix(auth): sanitize display_name before inserting the profile

A one-character name from auth metadata violated the profiles check
constraint inside the trigger, which aborted the entire signup. Falls back
to a default instead of raising.
```

Bad: `update stuff`, `fixes`, `wip`, `changes as requested`.

**Subject line rules:** imperative mood ("add", not "added"), no trailing period, under 72
characters. Breaking changes get a `!` after the scope and a `BREAKING CHANGE:` footer.

Small mechanical commits while you work are fine — the PR is squash-merged, so its **title**
is what lands in history and is what CI validates.

## Pull requests

- Keep them reviewable in one sitting. If a PR touches more than ~400 lines of real logic,
  it probably wants splitting.
- Fill in the template. "How to verify" means the exact steps, not "tested locally".
- UI changes need before/after screenshots.
- `npm run verify` must pass, and CI must be green.
- Squash-merge. The PR title becomes the commit subject, so write it as a Conventional
  Commit.

## Database changes

Migrations are **numbered and append-only.**

- Never edit a migration that has been applied anywhere. Corrections ship as a new file.
- Name files `NNNN_short_description.sql`, continuing the sequence.
- Every new table: `enable row level security`, an explicit grant, and at least one policy.
  A table with RLS on and no policy is unreachable — that is the intended failure mode, but
  make it deliberate.
- Anything that must stay correct under concurrent writers belongs in a `SECURITY DEFINER`
  function with a row lock, not in client code. See
  [`docs/adr/0002`](docs/adr/0002-participation-writes-through-rpcs.md).
- Add an assertion to `supabase/tests/` for behaviour worth protecting. CI runs the suite
  against real Postgres + PostGIS.

## Code

- TypeScript strict. No `any` — if a boundary is genuinely untyped, narrow it once at the
  edge and comment why.
- Feature-first: a change usually lives in one folder under `src/features/`.
- Prettier decides formatting. Do not argue with it in review.
- Comments explain _why_, not what. A comment restating the line below it is noise.
- User-facing copy is Spanish (Costa Rican). Code, comments, commits and docs are English.

## Issues

Use the templates. A good issue states whose problem it is — organizer or participant —
and what "done" looks like. Issues without acceptance criteria get sent back.

### Labels

| Prefix      | Values                                                       |
| ----------- | ------------------------------------------------------------ |
| `type:`     | `bug`, `feature`, `chore`, `docs`, `security`                |
| `area:`     | `discover`, `participation`, `organizer`, `auth`, `db`, `ci` |
| `priority:` | `p0-blocker`, `p1-high`, `p2-normal`, `p3-later`             |
| `status:`   | `triage`, `ready`, `in-progress`, `blocked`                  |

`p0-blocker` means the product is unsafe or unusable. It is not a synonym for urgent.

## What not to commit

- `.env`, real credentials, or any service-role key
- Real user data, including in test fixtures or screenshots
- `node_modules/`, build output, `ios/`, `android/` (regenerated by Expo prebuild)
- Large binaries — link them instead
